# Куриерска доставка — разделяне и live ценообразуване

**Дата:** 2026-07-24
**Статус:** одобрен дизайн, чака имплементация
**Свързано:** [[courier-integration-feature]], `2026-07-12-courier-integration-design.md`

## Проблем

Сегашният таб „Доставка" смесва два несъвместими модела в един редактор на методи:
1. **Ръчна доставка** (взимане от място, лична доставка) — собственикът определя цената.
2. **Куриер (Еконт/Спиди)** — цената е динамична (тегло/град/услуга/COD); собственикът НЕ я знае предварително.

Резултат: формата иска фиксирана цена дори за куриер (безсмислено), а свързването на куриер (таб „Куриери") и метода на доставка (таб „Доставка") са разделени → объркващо и наполовина работещо (checkout не показва office picker без ръчна конфигурация).

## Решение (одобрено)

Разделяне по **източник на истината за цената**:

### Таб „Куриери (Еконт, Спиди)" — цялата куриерска логика
За всеки куриер (когато е свързан):
- Ключове + подател + „Провери връзка" *(вече готово)*
- **+ настройка на доставка** (изнесено тук от таб „Доставка"):
  - Активирай доставка до **офис** и/или до **адрес** (два независими превключвателя)
  - **Резервна цена** (eur cents) — ползва се само ако куриерът не върне live цена
  - **Праг за безплатна доставка** (`freeOverCents`, опц.) — определя се от собственика

### Таб „Доставка" — само собствена доставка
Типове на метода стават само:
- **Взимане от място** (`pickup`) — пунктове с адрес + работно време
- **Лична доставка от производителя** (`local`) — работно време + цени по градове (ръчни)

Типът **`courier` се премахва** от този редактор.

### Ценова логика при checkout (приоритет)
1. **Праг за безплатна** — ако количка ≥ `freeOverCents` → доставка = **Безплатна** (не пита куриера).
2. **Live цена** — иначе викаме куриера (`calculate`) с тегло + дестинация → точната цена.
3. **Резервна цена** — ако live извикването се провали (timeout/грешка/липса на тегло) → фиксираната резервна цена на собственика.

**Един метод за доставка = един куриер = един `deliveryTarget`.** За Еконт И Спиди → два отделни куриерски метода (всеки в своя куриер).

## Архитектура

### Данни (Drizzle схема)
Ново: куриерската конфигурация за доставка се мести от `shipping_methods` към `shop_courier_accounts` (или нова таблица `courier_delivery_options`). **Решение:** нова таблица `courier_delivery_options` (per shop+provider+target), защото един куриер може да предлага И офис, И адрес с различни резервни цени:

```
courier_delivery_options
  id, shopId, provider (econt|speedy), deliveryTarget (office|address)
  active (bool)                       — предлага ли се този вариант
  displayName (text)                  — как се казва в checkout ("До офис на Спиди")
  fallbackPriceCents (int)            — резервна цена
  freeOverCents (int, nullable)       — праг за безплатна (собственикът)
  createdAt, updatedAt
  UNIQUE(shopId, provider, deliveryTarget)
```

`shipping_methods`: премахваме `courierProvider` + `deliveryTarget` от UI-редактора (колоните остават за обратна съвместимост/миграция, но `type` вече е само `pickup|local`).

### Live ценообразуване (нов слой)
`CourierProvider` интерфейс получава нов метод:
```
calculatePrice(input: PriceInput, creds): Promise<{ amountCents: number } | null>
```
- **Econt:** `LabelService.createLabel` с `mode: "calculate"` → `ShipmentStatus.totalPrice`.
- **Speedy:** `POST /calculate` → `calculations[0].price.total` (сверено на живо 2026-07-24).
- **Валута = EUR** — България прие еврото от 01.2026; куриерите връщат директно в евро
  (`"currency": "EUR"` потвърдено на живо от Speedy). Никаква конверсия: `total * 100` → eur cents.
  Ползваме `total` (с ДДС) — това е цената, която купувачът реално плаща.
- `null` при грешка → викащият пада на резервната цена.
- Извикването е с кратък timeout (напр. 6s) — checkout не бива да виси.

### Checkout (клиентска част)
- `PricedCart` вече поддържа `shipping.priceCents`. Разширяваме: при куриерски метод с избран офис/град → server action `getCourierPrice(shopId, provider, target, weightGrams, dest)` → връща live или резервна цена.
- Office picker се показва при `deliveryTarget === "office"` *(вече готово)*.
- Цената се преизчислява при смяна на офис/град (реалната цена зависи от дестинацията).
- `src/lib/pricing.ts` остава източник за subtotal/отстъпки; доставката се инжектира отвън (както сега).

### Server actions
- `saveCourierDeliveryOption(provider, target, {active, displayName, fallbackPriceCents, freeOverCents})` — в `src/actions/couriers.ts`, зад `requireShop`.
- `getCourierPrice(...)` — публичен (checkout), rate-limited, Zod вход, tenant по shopId.
- Товарителницата (`generateWaybill`) остава както е.

### Миграция на съществуващи данни
Сегашните `shipping_methods` с `type='courier'` → еднократен скрипт: за всеки такъв метод създай `courier_delivery_options` ред (provider+target от метода, `fallbackPriceCents` = сегашната цена, `freeOverCents` пренесен), после деактивирай стария метод. Демо/прод данни са малко (0 на прод) → нискорисково.

## Error handling
- Live извикване гръмне → резервна цена (не блокира поръчката).
- Няма свързан куриер → куриерската опция не се показва (`hasCourier` гард, вече има).
- Купувач без избран офис при `office` метод → сървърът блокира (вече има).
- Цената е в EUR (без конверсия); `Math.round(total * 100)` → eur cents.

## Тестване
- Unit: `calculatePrice` mapping (Econt calculate mode, Speedy /calculate) + fallback на null при грешка.
- Unit: приоритетна логика (безплатна > live > резервна).
- Жив тест: реална Speedy `/calculate` заявка (тест акаунт) + Econt demo calculate.
- E2e: checkout с куриерски метод → office picker → цена се показва.

## Извън обхвата (YAGNI)
- Множество куриери в един метод с избор на по-евтиния (объркващо).
- Кеширане на цени (live е достатъчно бързо; добавяме ако стане проблем).
- Автоматично тегло по обем/размери (ползваме `aggregateOrderWeight` + резервен грамаж).
